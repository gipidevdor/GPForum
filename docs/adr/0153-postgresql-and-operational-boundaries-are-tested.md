# ADR 0153: PostgreSQL and operational boundaries are tested

## Status

Accepted (2026-10-23).

## Context

Hot reload, schema review and attachment publication must hold through process
and storage failures. Query counts alone cannot prove that a request uses the
closed SQL function catalogue. Request diagnostics need a correlation id across
framework, application and controller logs.

## Decision

`before_server_start` runs in the Hypnotoad manager, before the fork. Warmup
already disconnects its schema; it now clears its marker and disconnects even
when rendering throws. The operations bootstrap also disconnects an existing
schema with warmup disabled. Creating a schema remains lazy. DBIx checks the
process id before obtaining a handle, sets InactiveDestroy on inherited handles
and opens a new connection in a child. Integration tests exercise manager
cleanup, failed warmup, an actual fork and the surviving parent connection.
No independent DBI pool is introduced beside the existing transaction owner.

On the disposable PostgreSQL matrix, pg_stat_statements records representative
public pages with caches cleared. The observer disables tracking on its own
connection and resets only the test database's statistics. It checks top-level
statements against the **entire SQL statement** generated by each current
catalogue entry, including typed placeholders. Only BEGIN/COMMIT/ROLLBACK are
additionally allowed. Nested SQL in an API implementation is intentionally
outside this application boundary. A direct ORM read is a negative control.
The test requires observed SQL, so a cached response cannot make it vacuous.
The preload is optional outside that matrix; production needs no extension.

The PostgreSQL 18 matrix compares a normalized pg_dump --schema-only with
`etc/schema/postgresql-18.sql` after the suite, retaining function bodies,
comments and grants. Other majors upload their native SQL dumps. Month
partitions, the diagnostics extension, client banners, owner annotations and
psql's random restriction key are excluded/normalized as documented beside
the snapshot. Tests prove deterministic output and failure on schema drift.
Migration files remain immutable; the snapshot is review evidence, not an
alternative installer.

Attachment writes create a private random temporary file beside the target,
flush its contents, restore the service umask's file permissions, sync it,
close it, rename it and sync the containing directory. Production uploads
remain group-readable (0640 with umask 0027) for the reverse proxy.
Newly created parent directory entries are synchronized before publication.
Only a fully successful write reaches `mark_uploaded` and the antivirus
verdict. Failed pre-rename writes preserve the old object; failed directory
sync reports failure even when the complete new file is visible. Orphaned
complete files after a crash remain subject to the existing lifecycle cleanup.
This is the explicit exception to ADR 0097 section 11: attachment bytes live
outside PostgreSQL WAL. Ordinary generated files/caches still use atomic
writes without paying for fsync. Filesystem/hardware guarantees still apply;
rename atomicity alone is not power-loss durability.

Mojo::Log emits one JSON object per physical line. Request context contains
the validated X-Request-ID, an HMAC of the session user id (null for guests),
and monotonic elapsed milliseconds. No email, IP, token or query parameter is
added to the context. The controller logger retains its own context for async
callbacks, while synchronous app logs inherit dispatch's dynamic scope.
Background logs have null request fields. Request completion records route
name, status and SQL duration. The DB statistics observer times SQL calls with
a monotonic clock, including errors from the function call layer;
DefaultHelpers emits numeric `app` and `db` Server-Timing
durations in **milliseconds**. The application timer measures dispatch until
response finalization, not network transfer or a WebSocket's lifetime.

Synchronous production dispatch captures Perl warnings in bounded
`perl.warning` JSON events with stack locations and no call arguments. It
performs no SQL and guards recursion. Jobs and delayed callbacks retain their
existing warning handlers. These operational events are not moderation reports
or chained audit records: pushing arbitrary warnings into those records would
add writes during database failures, leak arguments through stacks and let
warning storms flood staff workflows. A separately designed deduplicated
operational inbox can be added later if needed.

## Alternatives kept explicit

Sessions stay LOGGED. UNLOGGED tables are truncated after an unclean shutdown
and are not replicated to standby servers. GPForum supports failover and
server-side revocation; silently changing those contracts has no measured
benefit here. PostgreSQL does not promise a universal twofold improvement.
See [CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html).

pg_cron remains an opt-in deployment alternative, not a required extension or
an automatic replacement for the shipped systemd/rc/launchd jobs. An operator
would first install/preload it and deliberately migrate individual SQL-only
jobs, with timeouts, ownership, retry policy and duplicate scheduling checked.
Jobs that run Perl commands or touch attachments still need an OS process.
Use one scheduler per job; retain the existing advisory locks. A deployment
that chooses pg_cron documents the extension and restoration requirements.
See [pg_cron](https://github.com/citusdata/pg_cron).

## Verification

- `t/integration/postgres-query-catalogue.t`: connection ownership, warmup
  cleanup, closed query catalogue and forbidden ORM negative control.
- `t/integration/postgres-schema-snapshot.t`: canonical dump, determinism,
  check mode and a deliberate unrecorded table.
- `t/733-operational-logging.t`: JSON/Unicode, pseudonyms, warning stacks,
  background context and reverse-order delayed loggers.
- `t/734-attachment-durability.t`: real file/directory sync, failure before
  rename, failure after rename, complete bytes and private temporary files.
- `t/735-db-query-timing.t`: SQL time excludes rendering, counts nested
  connection setup once and does not leak into the next request.

The existing attachment, logging, DB statistics, warmup and deployment tests
continue to cover their contracts.
